Word 排版一致性双管线：Linux 转换 × Windows 真实打印

文本比对若只在 Linux 上用开源方案把 Word 转成「文字 + 坐标」，分页和折行可能与 Windows 上 Word / WPS 打印不一致。本仓库给出两条可独立部署、可交叉验证的管线；对照 UI 内置于 Linux Flask 服务，不在本 GitHub Pages 站点上运行。

没有浏览器里的实时转换。管线 A 需要本机 LibreOffice 7.6（UNO :2002）与 Flask（:8899）；管线 B 需要 Windows 上的 XPS 打印节点（:8090）。以下页面只说明架构、部署与仓库中已记录的测试，不代替自建服务。

01 · 问题

解决什么问题

README 描述的场景：文本比对服务部署在 Linux 上。用 LibreOffice 等开源方案把 Word 转成 PDF，再解析「文字 + 坐标」时，分页与折行结果可能和 Windows 上 Word / WPS 直接打印的排版不一致（窜行、窜页），从而导致比对误判。

仓库提供一套可独立部署、可交叉验证的双管线，而不是单一「云端排版引擎」：

摘自 README.md / README_EN.md 的管线对照。授权成本列为项目文档中的表述，不是商业报价。
管线环境技术路线文档中的授权成本
A · linux-pipeline Linux LibreOffice headless + UNO 折行修复器 → PDF → pdfplumber 解析文字 + 坐标 文档写为零（全开源依赖）
B · windows-printnode Windows 真实 Word / WPS 打印到 XPS 虚拟打印机 → 解析 XPS 文字 + 坐标 + 页面渲染图 复用机器上已有的 Office 授权（见授权节）
对比页 内置于 A 上传 Word → 双管线同跑 → 总体判定 + 逐页并排渲染 + 逐行文字/坐标对照 —

源码中的打印引擎实现见 PrintParseService.cs：若存在 Word.Application ProgID 则使用 WordComPrintEngine（引擎名 word），否则回退 WordpadPrintEngine（引擎名 wordpad-placeholder）。注释写明 WordPad 排版不等于 Word，仅用于打通管线。源码没有单独的 WPS COM 引擎类；README 将 Word / WPS 打印作为对照基准来描述。

03 · 折行

为什么 LibreOffice 转 PDF 会和打印不一致

README 的说明：LibreOffice 与 Word 的折行规则不同。最典型的一类是「数字串 + 全角标点」长串——Word / WPS 视其为可逐字断开的序列，而 LibreOffice 将其当作不可拆分的西文单词整体推入下一行，造成整行下移、内容窜页。

uno_linewrap_fix.py 通过 UNO API 读取文档真实字体、字号与行宽，按源码注释中「从基准 PDF 逆向」的两套模型模拟断行，并在转换前插入显式 LINE_BREAK：

  • token 模型（simulate_breaks_token）：段落含「数字,数字」胶合时使用；数字/半角逗号点连串可再粘一个全角标点，断点只在 token 末尾。
  • 压缩逐字模型（simulate_breaks_compressed）：全角标点数字串；ASCII 宽约 0.492em，否则 0.92em。
  • 仅处理匹配 [0-9、，。,．]{60,} 的段落；其他段落不动。
  • 页心宽度取自页面样式；源码用约 4.6pt 的 Word/LO 宽度差，以及 token 路径上的 14.1pt 标点悬挂余量（按字号缩放）。
  • 连接 127.0.0.1:2002 的 UNO socket（start_uno.sh / lo-uno.service）。

README 写到：在所列生产/实测文档上，输出与 Windows 打印基准逐页行数一致。这是文档中对那些样本的记录，不是对任意 Word 文件的保证。见实测验证与局限。

04 · 运行时

双管线与对比页（源码路径）

管线 A · linux-pipeline/app.py

Flask 监听 0.0.0.0:8899，上传上限 50 MiB，仅 .doc / .docx。

  1. 优先用 LibreOffice 自带 Python 调用折行修复器，写出 PDF。
  2. 修复失败或产物过小则回退 soffice --headless --convert-to pdf:writer_pdf_Export（回退路径不再插入断行）。
  3. pdfplumber.extract_words，Y_TOL = 3.5（注释：来自 Windows 双管线实测，填空文字基线漂移 2.1pt，容差须 ≥3pt），按 top 聚类成行。
  4. 可选：POST {XPS_API}/api/print-parse。默认 XPS_API=http://127.0.0.1:8090。XPS 坐标乘 0.75（96 dpi → PDF pt）。过滤纯空白行，保留 raw_line_count。

管线 B · PrintParseService.cs

HttpListener 前缀 http://+:8090/。作业在 STA 线程打印并解析（WPF 渲染要求）。

  1. 打印到已由 setup.ps1 固定文件端口的 Microsoft XPS Document Writer（C:\printnode\print\output.xps）。
  2. 手动导航 XPS OPC（绕过交错 XPS 上 GetFixedDocumentSequence 可能为 null）。
  3. OpenXPS 命名空间替换为 WPF 可加载的 MS XPS 命名空间；Glyphs 抽字，基线容差 3.0 聚行。
  4. 页面以 2× RenderTargetBitmap 出 PNG。

对比页判定（内嵌于 Flask，非本站）

app.py 中的页面：总体判定在 XPS 可用时比较各页行数是否相等；逐行表对文字做空白归一化比较，并显示 Δtop / Δx0。界面将 Δtop > 2.5 或 Δx0 > 3.5 标为「坐标漂移」。B 失败时展示 xps_error，不假装两侧都成功。

06 · 部署

部署与测试方式

Pipeline A · Linux

README 写明在 CentOS 7 上验证通过。步骤与仓库一致：

# 1. 将 LibreOffice 7.6 装到 /opt/libreoffice7.6（版本固化，勿随意升级）

# 2. 部署代码
mkdir -p /opt/word2pdf-test
cp linux-pipeline/{app.py,uno_linewrap_fix.py,requirements.txt} /opt/word2pdf-test/
python3 -m venv /opt/word2pdf-test/venv
/opt/word2pdf-test/venv/bin/pip install -r /opt/word2pdf-test/requirements.txt

# 3. 注册并启动服务
cp linux-pipeline/{lo-uno.service,word2pdf-test.service} /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now lo-uno word2pdf-test

# 4.（可选）接入管线 B
systemctl edit word2pdf-test   # Environment=XPS_API=http://<windows节点IP>:8090

部署完成后打开 http://<服务器>:8899 上传 .doc / .docx。该地址是你自己的主机，不是本 GitHub Pages 域名。

Pipeline B · Windows

README：无需虚拟机，任一已安装 Word 或 WPS 的办公电脑可作节点。管理员 PowerShell 在 windows-printnode 目录执行：

powershell -NoProfile -ExecutionPolicy Bypass -File .\setup.ps1

setup.ps1 会：创建 C:\printnode；放行 8090 与 URL ACL；将 Microsoft XPS Document Writer 端口钉到 C:\printnode\print\output.xps；用系统 csc.exe（.NET Framework 4.x）编译；注册 PrintParseService 计划任务。脚本还包含 RDP、高性能电源方案与关闭自动更新等本机设置——部署前请按你的安全策略审阅。

管线 B HTTP API（:8090），摘自 README 与 PrintParseService.cs。
方法路径说明
GET/health健康检查；JSON 含 status、engine（word 或 wordpad-placeholder）、printer
POST/api/print-parsemultipart 字段 file，返回每页文字 + 坐标 + image_url
GET/images/{job}/{n}.png页面渲染图

可选无人值守 VM：将 autounattend.xml、setup.cmd、setup.ps1、PrintParseService.cs 打成 ISO。应答文件密码占位符为 CHANGE-ME-Password，使用前必须替换。

本站（GitHub Pages）如何发布

仓库 .github/workflows/pages.yml 在推送到 main 时用官方 actions/configure-pages、upload-pages-artifact、deploy-pages 发布 docs/。仓库设置需选择 GitHub Actions 作为 Pages 源。预期地址：https://unstoppablecurry.github.io/word-print-layout-pipeline/。

09 · 边界

局限与本站不会声称的内容

  • 无在线演示。本域名只有静态 HTML/CSS/SVG。不能上传 Word，也不能调用 :8899 / :8090。
  • UNO 修复范围有限。只处理 ≥60 字符的数字/指定标点长串段落；模型由特定基准校准，不是完整的 Word 排版引擎。
  • 回退会失去修复。convert_to_pdf 在 UNO 失败时走裸转换，折行仍可能与打印不一致。
  • WordPad 回退不是打印基准。未安装 Word 时引擎名为 wordpad-placeholder，源码写明排版 ≠ Word。
  • 对比页以行数为主。「总体判定」比的是每页行数；文字与坐标另有容差，坐标接近不等于视觉像素级一致。
  • 样本表不是全体正确率。README 的 100% 逐页行数一致仅针对表中文档，不外推到未测文件、未测 LO 版本或未测打印机驱动。
  • 版本钉死。文档要求 LibreOffice 7.6 装在 /opt/libreoffice7.6，不要随意升级。Linux 侧写明 CentOS 7 验证；未声称其他发行版已测。
  • 无客户、性能或 SLA 数据。本站不编造部署客户、吞吐、时延或「全平台支持」。
